# 公司 RPA 设计规则

## 适用场景

当财务自动化需求包含多个执行步骤、SAP/OA/PDF/邮件/数据库/Excel 模板等外部系统或人工复核节点时，优先按公司 RPA 项目方式设计，而不是把全部逻辑塞进一个脚本。

## 核心原则

- 先产出确认稿，再写完整代码。确认稿必须列出步骤拆分、输入输出、运行人员、可重跑边界、交接文件、待确认事项和验证方式。
- 参数选择、数据下载、业务加工、结果输出、发布发送分层处理；不要让下载脚本承担业务计算，也不要让输出脚本重新下载数据。
- 每一步都应能说明：输入是什么、输出是什么、失败后如何重跑、是否会覆盖历史结果、谁负责复核。
- 外部系统步骤（SAP、OA、网页、PDF、邮件）默认独立成可重跑步骤，便于失败后只重跑该层。
- 涉及公司/期间/路径/运行批次的项目，优先设置第一步参数选择脚本，写入配置并创建目录；包含 SAP 下载时默认保留 `01-公司期间选择.py`。
- 后续加工步骤读取前一步稳定落地的文件或数据库表，不直接依赖外部系统实时状态。

## 推荐步骤分层

| 层次 | 常见脚本 | 职责 | 不应混入 |
| --- | --- | --- | --- |
| 参数层 | `01-公司期间选择.py` | 录入公司、期间、路径、运行批次，写配置，建目录，必要时备份上期数据 | 下载或业务计算 |
| 获取层 | `02-SAP数据下载-*.py`、`02-OA数据下载-*.py` | 从外部系统下载原始数据，保存原始 Excel/PDF | 清洗、匹配、报表口径 |
| 导入层 | `03-数据库导入-*.py` 或 `03-手工导入.py` | 校验字段、写入数据库或过程文件，保留导入日志 | 最终结果输出 |
| 加工层 | `04-数据处理-*.py` | 清洗、匹配、计算、生成过程表和校验表 | 外部系统点击下载 |
| 输出层 | `05/07-结果输出.py` | 写入 Excel 模板、复制公式/格式、生成最终文件 | 改变下载范围或重新取数 |
| 发布层 | `09-HTML报告.py`、`12-邮件发送.py` | 展示、汇总、发送 | 改写核心计算口径 |

编号按项目既有习惯调整，但职责边界应保持清晰。

## 确认稿必须包含

- 步骤清单：脚本编号、脚本名、运行顺序、责任人或运行角色。
- 输入输出清单：每一步读取哪些文件/表/Sheet，输出到哪里，文件命名和覆盖规则。
- 重跑策略：失败后重跑当前步骤是否会覆盖旧结果；哪些步骤可只补跑缺失文件，哪些必须全量重跑。
- 人工复核节点：哪些过程表、校验表、未匹配清单或异常清单需要人工确认。
- 配置与目录：配置文件 section、公司/期间字段、原始数据目录、运行结果目录、备份目录。
- 外部系统边界：SAP/OA/PDF/邮件等步骤是否实际验证过；未验证时只声明语法或静态检查。

## 数据库与界面项目

- 数据库只保存需要追溯、共享、复核或多人维护的数据；不要为了临时中间结果过度建表。
- Web/桌面界面只做维护、查看、导入导出和操作留痕时，不要把最终报表生成逻辑混进界面按钮，除非用户明确要求。
- 业务可编辑表默认需要唯一定位列、操作日志、停用/恢复策略和导入日志。
- 已建库项目如果字段变更，必须提醒用户 `CREATE TABLE IF NOT EXISTS` 不会修改旧表，必要时另给迁移 SQL。

## 可复用项目治理规则

- 多步骤项目建议维护运行状态表：记录 RPA 代码、运行期间、公司、最大步骤、当前步骤、当前状态、结果状态、最后更新时间和运行用户；每一步完成后更新状态，失败时保留失败步骤，便于只重跑后续步骤。
- 当上游下载、手工导入或配置数据发生变化时，下游结果应标记为“需重新生成”，不要让旧结果静默继续展示为完成。
- RPA 配置维护脚本可采用“读取旧表、清洗新表、按主键对比、拆分新增/更新/停用”的模式；对权限表、菜单表等衍生配置，要随主表同步新增、停用或删除。
- 参数选择界面可复用 `text/dropdown/multi_dropdown/date` 四类输入控件；期间字段默认校验为 `YYYYMM`，多选字段返回稳定列表，默认值和可选项应来自配置或数据库，而不是散落硬编码。
- 数据库连接字符串、账号密码、内网地址和共享盘真实路径不得写入 skill 或 GitHub 记录；如原项目存在 `${B64:...}` 形式密码解码，只沉淀“支持解码/脱敏读取”的模式，不沉淀真实密文。
- 查询/维护界面默认支持：左侧业务菜单、表格筛选、清除筛选、选择显示列、导出当前筛选结果；可编辑表必须有唯一定位列、待保存高亮、保存确认、撤销修改和操作日志。
- 表头筛选控件要跟随当前显示列布局重建；切换菜单、选择显示列、刷新数据后，要同步清理或重建筛选状态，避免筛选控件和列位置错位。
- 导出当前表格时要区分“当前显示列”和“全部列”，并明确是否只导出当前筛选行。

## 版本3采购大表可复用规则

- 参数层应把公司文本解析成稳定列表，并明确 KUS、AWS、GROUP 三种运行模式；集团或跨系统场景要先确认是否拆成多轮外部系统下载。
- 每个会被后续步骤复用的生成范围，应写入业务配置 section，例如 `company_text`、`period_start_date`、`period_end_date`；查询界面和下游生成默认读取该范围生成初始筛选。
- 数据库写入优先使用中文字段安全转义、参数化查询、字段白名单和 `chunksize`；涉及中文列名时统一使用 `quote_identifier()` 类函数包裹反引号。
- 原始/结果表按期间、公司或公司+期间重跑时，先删除同范围旧数据再追加；若表为空可重置自增，但不得重置仍有历史数据的表。
- 手工配置表按唯一键 upsert：读取线下维护文件时允许“文件不存在则跳过”，但必填表或唯一键缺失必须报错；写库列只能取数据库已有字段，自动补 `更新人工号`、更新时间类字段。
- 若结果表允许人工改动，应在运行状态中记录“单体手工已修改”或“集团手工已修改”；自动重生成时先取人工修改的公司期间组合并跳过，避免覆盖人工修正。
- 下游集团/汇总步骤必须做前置检查：运行状态达到指定步骤、单体结果表存在数据、依赖清单有匹配范围，三者不满足时跳过并打印被跳过的公司期间。
- 宽表多字段转长表可采用 `melt` 模式，例如 `净额法料号1-5` 转成一列物料编码；转长表后补期间、公司、供应商、导入时间、更新人工号，并按业务唯一键去重。
- 资产主数据这类来源于分批 SAP 文件的数据应单独建表，字段保留 `系统来源` 与 `批次标识`，不要混入手工维护主数据表；唯一键优先覆盖期间、系统来源和业务主键。
- PyQt 查询/编辑界面若复用版本3模式，应包含 `DataFrameModel` 式变更追踪：临时新增行 key、黄色高亮待保存单元格、复制行、删除行、粘贴 Excel 区域、统一保存、操作日志。
- 配置表可按确认开放新增/复制/删除；结果表默认只允许修改现有行。新增/删除结果表行会影响审计口径，必须先让用户确认。
- 筛选候选值应合并数据库 distinct 值和当前界面模型中的未保存值；保存成功后清理当前表缓存，切换列显示或刷新数据后重建筛选控件。

## 代码交付风格

- 默认输出 Jupyter/Spyder 友好的顺序执行 `.py` 文件，普通注释分段即可，不要求 `# In[ ]:`。
- 除非用户明确要求 CLI、服务化、可导入模块或调度平台封装，不默认使用 `main()` 包装执行流程。
- 生成或修改后至少运行 `python -m py_compile`；真实外部系统点击、下载、邮件发送只有实际运行后才能声明验证完成。
